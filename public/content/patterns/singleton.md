**Singleton** гарантирует, что у класса есть только один экземпляр, и даёт к нему глобальную точку доступа. Самый известный паттерн — и самый критикуемый: в классическом виде это глобальная переменная с дополнительными шагами.

## Классическая реализация

```ts
export class Config {
  static #instance: Config | undefined;
  readonly apiUrl = '/api';

  private constructor() {} // нельзя создать через new

  static getInstance(): Config {
    Config.#instance ??= new Config();
    return Config.#instance;
  }
}

const config = Config.getInstance();
```

## Почему это антипаттерн

- **Скрытые зависимости**: класс, вызывающий `Config.getInstance()` внутри метода, не показывает это в сигнатуре.
- **Тестирование**: нельзя подменить экземпляр, состояние переживает тесты и делает их зависимыми друг от друга.
- **Глобальное изменяемое состояние**: любой код может изменить синглтон.
- **Нарушение SRP**: класс отвечает и за свою логику, и за управление своим жизненным циклом.

## Модульный синглтон

ES-модуль выполняется один раз — экспортированный объект естественным образом единственный:

```ts
// analytics.ts
export const analytics = createAnalyticsClient({ key: 'pk_...' });
```

Просто, но проблемы тестирования и скрытых зависимостей остаются.

## Синглтон в Angular: через DI

```ts
@Injectable({ providedIn: 'root' })
export class SessionStore {
  readonly user = signal<User | null>(null);
}
```

Один экземпляр на приложение — но:

- **«Один» решает конфигурация, а не класс.** Тот же класс в `providers` компонента даст отдельный экземпляр на компонент.
- **Зависимость явная**: `inject(SessionStore)`.
- **Подмена в тестах**: `{ provide: SessionStore, useValue: fakeStore }`.
- **Ленивость и tree-shaking**: создаётся при первом `inject`, удаляется из бандла, если не используется.

> [!WARNING]
> Подвох: сервис в `providers` ленивого маршрута или компонента — уже не синглтон приложения. Если вы видите «два разных состояния корзины», проверьте, не указан ли `CartService` дополнительно в чьих-то `providers`.

## Когда единственность действительно нужна

- Кеш, общий для приложения.
- Соединение WebSocket, пул ресурсов.
- Состояние пользовательской сессии.
- Обёртка над глобальным API браузера.

Во всех случаях в Angular — `providedIn: 'root'` (или провайдер в `bootstrapApplication`), а не `static getInstance()`.

> [!INTERVIEW]
> «Почему Singleton называют антипаттерном и как это решается в Angular?» — Классический синглтон — глобальное состояние со скрытой зависимостью: его трудно подменить в тестах, и он сам управляет своим жизненным циклом. В Angular единственность обеспечивает DI-контейнер: сервис с `providedIn: 'root'` создаётся один раз на корневой инжектор, зависимость явно запрашивается через `inject()` и легко подменяется провайдером в тестах.

## Коротко

- Singleton — один экземпляр и глобальный доступ.
- Классическая реализация мешает тестам и скрывает зависимости.
- В Angular «одиночество» — свойство конфигурации DI: `providedIn: 'root'`.
- Повторный провайдер в `providers` создаёт новый экземпляр.
