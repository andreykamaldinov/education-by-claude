Производительность Angular-приложения складывается из двух частей: **загрузка** (сколько кода и данных нужно до первого полезного экрана) и **работа** (насколько дёшево обновлять интерфейс). `@defer` решает первую задачу прямо в шаблоне, остальные приёмы — вторую.

## @defer: ленивые части шаблона

```html
<app-product-header [product]="product()" />

@defer (on viewport) {
  <app-reviews [productId]="product().id" />
} @placeholder (minimum 300ms) {
  <div class="reviews-skeleton"></div>
} @loading (after 150ms; minimum 400ms) {
  <app-spinner />
} @error {
  <p>Не удалось загрузить отзывы.</p>
}
```

Компоненты, директивы и пайпы внутри `@defer` **выносятся в отдельный чанк** и загружаются только при срабатывании триггера. Условие: они standalone и не используются в этом же файле вне `@defer`.

| Блок | Назначение |
| --- | --- |
| `@placeholder` | показывается до срабатывания триггера; `minimum` — минимальное время показа |
| `@loading` | во время загрузки чанка; `after` — показать только если загрузка дольше, чем N мс |
| `@error` | если загрузка не удалась |

### Триггеры

| Триггер | Когда загружать |
| --- | --- |
| `on idle` (по умолчанию) | когда браузер простаивает (`requestIdleCallback`) |
| `on viewport` | когда placeholder попал в область видимости |
| `on interaction` | клик или keydown по placeholder или указанному элементу |
| `on hover` | наведение / фокус |
| `on immediate` | сразу после рендера страницы (не блокируя её) |
| `on timer(2s)` | через заданное время |
| `when condition()` | когда выражение стало истинным (один раз) |

Можно комбинировать и разделять загрузку и показ через **prefetch**:

```html
@defer (on interaction; prefetch on idle) {
  <app-rich-editor />
} @placeholder {
  <button>Редактировать</button>
}
```

Код редактора загрузится в фоне, когда браузер свободен, а покажется по клику — без задержки.

> [!TIP]
> Хорошие кандидаты для `@defer`: всё ниже первого экрана, тяжёлые библиотеки (графики, редакторы, карты), редко используемые панели и модальные окна, виджеты для части пользователей.

## Изображения: NgOptimizedImage

```html
<img ngSrc="/images/hero.jpg" width="1200" height="600" priority />
<img ngSrc="avatar.jpg" width="48" height="48" />
<img ngSrc="banner.jpg" fill sizes="(max-width: 768px) 100vw, 50vw" />
```

Директива:

- требует `width`/`height` (или `fill`) — предотвращает сдвиги макета (CLS);
- по умолчанию ставит `loading="lazy"`, а для `priority` — `fetchpriority="high"` и подсказку preload (для LCP-изображения);
- генерирует `srcset` при подключённом загрузчике CDN;
- предупреждает в dev-режиме о типичных ошибках (слишком большой файл, LCP без `priority`).

## Списки

```html
@for (row of rows(); track row.id) {
  <app-row [row]="row" />
}
```

- `track` по стабильному id — Angular переиспользует DOM-узлы при обновлении данных.
- Для тысяч строк — виртуальная прокрутка `cdk-virtual-scroll-viewport` (рендерятся только видимые строки) или пагинация.

## Обновления интерфейса

- **OnPush + сигналы** (по умолчанию в Angular 22): проверяются только изменившиеся компоненты.
- **computed вместо методов** в шаблоне.
- **Чистые пайпы** для форматирования.
- **Частые события** (`scroll`, `mousemove`, `resize`) — с `throttle`/`debounce` или вне шаблона.
- **Тяжёлые вычисления** — в Web Worker (`ng generate web-worker`).

## Размер бандла

```bash
ng build --stats-json
npx esbuild-visualizer --metadata dist/app/stats.json --open
```

- Бюджеты в `angular.json` (`budgets`) ломают сборку при превышении размера.
- Предупреждения CLI о CommonJS-зависимостях — сигнал искать ESM-альтернативы.
- Импортируйте точечно (`lodash-es`), избегайте барелей, тянущих лишнее.
- `providedIn: 'root'` делает сервисы tree-shakable.
- Шрифты и картинки — современные форматы (woff2, AVIF/WebP), локальный хостинг шрифтов.

## SSR и гидрация

Серверный рендеринг улучшает время первого отображения (FCP/LCP), а **incremental hydration** с `@defer (hydrate on ...)` откладывает гидрацию частей страницы до взаимодействия. Подробно — в уроке [SSR и гидрация](/tracks/angular/ssr-hydration).

## Измерение

1. **Lighthouse / PageSpeed Insights** — лабораторные метрики загрузки.
2. **Chrome DevTools → Performance** — long tasks, layout, рендеринг. Angular добавляет свою дорожку с метками компонентов и change detection.
3. **Angular DevTools → Profiler** — какие компоненты проверялись и сколько это заняло.
4. **Web Vitals в продакшене** — LCP, INP, CLS реальных пользователей (`web-vitals` библиотека). См. [Core Web Vitals](/tracks/web/web-vitals).

> [!WARNING]
> Не оптимизируйте вслепую. Сначала измерьте, найдите узкое место, исправьте, измерьте снова. Самые частые реальные проблемы: огромный initial bundle, неоптимизированные изображения, тяжёлый сторонний скрипт и лишние проверки в больших таблицах.

> [!INTERVIEW]
> «Как ускорить загрузку Angular-приложения?» — Ленивая загрузка маршрутов и `@defer` для тяжёлых частей страницы; контроль бюджета бандла и замена тяжёлых/CommonJS-зависимостей; `NgOptimizedImage` с `priority` для LCP-изображения; SSR с гидрацией (инкрементальной для ниже первого экрана); предзагрузка критичных ресурсов; кеширование и сжатие на сервере. Для отзывчивости — OnPush, сигналы, `track` в списках, виртуальный скролл, вынос вычислений в воркер.

## Коротко

- `@defer` выносит часть шаблона в отдельный чанк; триггеры `on viewport`, `on interaction`, `prefetch`.
- `NgOptimizedImage`: размеры, lazy loading, `priority` для LCP.
- `track` по id, виртуальный скролл для длинных списков.
- OnPush + сигналы + `computed` — дешёвые обновления.
- Измеряйте: Lighthouse, Performance, Angular DevTools, Web Vitals.
