Событийная архитектура (Event-Driven Architecture, EDA) строит взаимодействие компонентов вокруг **событий** — фактов о том, что произошло: «заказ оформлен», «оплата прошла», «товар закончился». Производители публикуют события, потребители реагируют, не зная друг о друге.

## Событие, команда, запрос

| | Событие | Команда | Запрос |
| --- | --- | --- | --- |
| Смысл | факт в прошлом | намерение | вопрос |
| Имя | `OrderPlaced` | `PlaceOrder` | `GetOrder` |
| Получатели | 0..N, неизвестны отправителю | ровно один обработчик | один |
| Можно отказаться? | нет — уже произошло | да | — |

## Брокеры сообщений

### RabbitMQ — очереди и маршрутизация

```text
Producer ──▶ Exchange ──(routing key)──▶ Queue A ──▶ Consumer A
                       └──────────────▶ Queue B ──▶ Consumer B
```

- Сообщение доставляется потребителю и **удаляется** из очереди после подтверждения (ack).
- Гибкая маршрутизация (direct, topic, fanout exchanges).
- Хорош для задач (task queues), RPC поверх очередей, сложной маршрутизации.

### Apache Kafka — распределённый лог

```text
Topic "orders", partition 0: [e1][e2][e3][e4][e5] ...
                                      ↑ offset группы «склад»
                                               ↑ offset группы «аналитика»
```

- Сообщения **хранятся** в логе заданное время (дни, месяцы, бессрочно), а не удаляются после чтения.
- Каждая группа потребителей хранит свой offset — можно перечитать историю, добавить нового потребителя «с начала».
- Порядок гарантирован **внутри партиции** (ключ сообщения, например `orderId`, определяет партицию).
- Огромная пропускная способность; основа для event sourcing, стриминга, интеграций.

| | RabbitMQ | Kafka |
| --- | --- | --- |
| Модель | очередь сообщений | журнал событий |
| После чтения | удаляется | хранится |
| Повторное чтение | нет | да (по offset) |
| Порядок | в очереди | в партиции |
| Сильные стороны | маршрутизация, задачи | поток событий, история, масштаб |

## Гарантии доставки

| Гарантия | Значит | Цена |
| --- | --- | --- |
| at-most-once | 0 или 1 раз — возможна потеря | самая простая |
| at-least-once | 1 или больше — возможны дубли | стандарт; нужна идемпотентность |
| exactly-once | ровно один раз | сложно, ограниченно (транзакции Kafka внутри экосистемы) |

На практике: **at-least-once + идемпотентные потребители** (дедупликация по id события).

## Eventual consistency

После события разные части системы обновляются в разное время. Пользователь оформил заказ, а в «Моих заказах» его ещё нет — модель чтения не успела обработать событие.

Как с этим жить во фронтенде:

- **Оптимистичный UI**: сразу показать результат, откатить при ошибке.
- **Показывать процесс**: статус «обрабатывается» вместо мгновенного «готово».
- **Чтение своей записи**: после команды использовать ответ команды (созданный заказ), а не сразу перечитывать список.
- **Push-уведомления** о завершении (WebSocket, SSE).

```ts
async placeOrder(cart: Cart) {
  const pending: Order = { id: crypto.randomUUID(), status: 'processing', items: cart.items };
  this.orders.update((list) => [pending, ...list]); // оптимистично
  try {
    const created = await firstValueFrom(this.api.place(cart, { idempotencyKey: pending.id }));
    this.orders.update((list) => list.map((o) => (o.id === pending.id ? created : o)));
  } catch {
    this.orders.update((list) => list.filter((o) => o.id !== pending.id)); // откат
    this.notify.error('Не удалось оформить заказ');
  }
}
```

## Схемы и версионирование событий

События — публичный контракт между командами. Правила:

- Описывайте схемы (JSON Schema, Avro, Protobuf) и храните их в реестре.
- Изменения — **обратно совместимые**: добавлять необязательные поля можно, удалять и переименовывать — нет (только новой версией события).
- Включайте метаданные: `eventId`, `occurredAt`, `version`, `correlationId`.

```json
{
  "eventId": "e7c1…",
  "type": "OrderPlaced",
  "version": 2,
  "occurredAt": "2026-10-29T13:41:00Z",
  "data": { "orderId": "ord_42", "total": { "amount": 4990, "currency": "RUB" } }
}
```

## Событийность во фронтенде

Идеи EDA видны и в клиентском коде:

- DOM-события и `CustomEvent`.
- Actions NgRx как события («[Каталог] Товар добавлен в корзину»), на которые реагируют несколько редьюсеров и эффектов.
- Шина между микрофронтендами (`CustomEvent` на `window`, `BroadcastChannel`).
- Real-time события с сервера через WebSocket/SSE, превращённые в потоки RxJS.

> [!INTERVIEW]
> «Чем Kafka отличается от RabbitMQ?» — RabbitMQ — брокер очередей: сообщение маршрутизируется в очереди и удаляется после подтверждения потребителем; силён в маршрутизации и распределении задач. Kafka — распределённый журнал событий: сообщения хранятся заданное время, каждая группа потребителей читает со своего offset и может перечитать историю; порядок гарантирован внутри партиции; подходит для потоков событий, event sourcing и интеграций с высокой нагрузкой.

## Коротко

- Событие — факт в прошлом; отправитель не знает получателей.
- RabbitMQ — очереди и маршрутизация; Kafka — журнал с историей и партициями.
- Стандарт — at-least-once + идемпотентные потребители.
- Eventual consistency требует оптимистичного UI и показа статуса процессов.
- События — контракт: схемы, версии, только совместимые изменения.
