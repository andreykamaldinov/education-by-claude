«Монолит или микросервисы?» — вопрос, который на системном дизайн-интервью задают и фронтендерам: от него зависят API, деплой, команды и то, как устроен фронтенд (вплоть до микрофронтендов). Правильный ответ почти всегда начинается со слов «зависит от…».

## Монолит

Одно приложение, одна кодовая база, один процесс развёртывания, обычно одна база данных.

```text
┌──────────────────────────────────────┐
│  Монолит                             │
│  каталог · корзина · заказы · оплата │
│  пользователи · уведомления          │
└───────────────┬──────────────────────┘
                ▼
           одна база данных
```

| Плюсы | Минусы |
| --- | --- |
| простая разработка, отладка, тестирование | растущая связанность («большой ком грязи») |
| вызовы — обычные функции: быстро и транзакционно | долгие сборки и тесты, страшные релизы |
| один деплой, простая инфраструктура | масштабируется только целиком |
| легко рефакторить сквозь границы | много команд мешают друг другу в одном коде |

## Модульный монолит

Один процесс развёртывания, но код строго разделён на модули по бизнес-контекстам с явными публичными API и запретом лезть во внутренности соседей (часто — со своими схемами в общей БД).

```text
┌─────────────────────────────────────────────┐
│ ┌─Каталог─┐ ┌─Заказы──┐ ┌─Оплата─┐ ┌─Users─┐ │  один деплой
│ │ API     │ │ API     │ │ API    │ │ API   │ │  модули общаются
│ └─────────┘ └─────────┘ └────────┘ └───────┘ │  только через API
└─────────────────────────────────────────────┘
```

Это часто лучший выбор по умолчанию: дисциплина границ без распределённой сложности. Если позже понадобится, модуль с чёткими границами выносится в отдельный сервис почти механически.

## Микросервисы

Набор небольших самостоятельно развёртываемых сервисов, каждый — вокруг одной бизнес-возможности, со своей базой данных, общающихся по сети.

```text
           ┌──────────── API Gateway / BFF ────────────┐
           ▼               ▼               ▼            ▼
      Каталог          Заказы          Оплата      Уведомления
        │ БД             │ БД            │ БД           │ очередь
        └────── события через брокер (Kafka / RabbitMQ) ─┘
```

| Плюсы | Минусы |
| --- | --- |
| независимый деплой и релизный цикл команд | распределённая система: сеть ненадёжна, задержки |
| масштабирование отдельных частей | нет общих транзакций — saga, eventual consistency |
| разные технологии под задачу | сложная отладка: трассировка, логи, мониторинг |
| изоляция отказов (при правильном дизайне) | дублирование данных и контрактов, версионирование API |
| границы контекстов закреплены физически | DevOps-нагрузка: CI/CD, оркестрация, сервис-меш |

## Когда переходить

Микросервисы решают **организационные** проблемы масштаба (много команд, независимые релизы) ценой **технической** сложности. Признаки, что пора:

- десятки разработчиков мешают друг другу в одном репозитории и релизе;
- части системы имеют разные требования к масштабированию и надёжности;
- границы доменов понятны и стабильны;
- есть зрелая инфраструктура: CI/CD, наблюдаемость, контейнеры.

Признаки, что рано: маленькая команда, продукт ищет себя, границы доменов меняются каждый месяц. Распределённый монолит — микросервисы, которые нельзя развернуть независимо, потому что они тесно связаны, — худшее из обоих миров.

> [!NOTE]
> Закон Конвея: архитектура системы повторяет структуру коммуникаций организации. Микросервисы работают, когда у каждого сервиса есть команда-владелец. «Обратный манёвр Конвея» — проектировать команды под желаемую архитектуру.

## Что это меняет для фронтенда

- **Агрегация данных**: экран заказа требует данных из пяти сервисов. Без промежуточного слоя фронтенд делает пять запросов и склеивает ответы. Решения — API Gateway, BFF или GraphQL federation ([Микросервисы: коммуникация и шлюзы](/tracks/architecture/microservices)).
- **Частичные отказы**: сервис рекомендаций упал — страница товара должна работать. UI проектируется с деградацией: блоки с отдельными состояниями загрузки и ошибок.
- **Eventual consistency**: после оформления заказа список заказов может обновиться не сразу.
- **Версионирование API**: сервисы выпускаются независимо — фронтенд должен переживать добавление полей и знать о депрекейтах.
- **Микрофронтенды** — продолжение той же идеи на клиенте, когда команды владеют вертикальными срезами продукта ([Микрофронтенды](/tracks/architecture/micro-frontends)).

> [!INTERVIEW]
> «Когда стоит переходить на микросервисы?» — Когда организационные проблемы масштаба (много команд, конфликты релизов, разные требования к масштабированию частей) перевешивают стоимость распределённой системы, а границы доменов уже понятны и стабильны. Начинать обычно лучше с модульного монолита со строгими границами модулей: он даёт дисциплину без сетевой сложности, а модули с чёткими API потом можно выделить в сервисы.

## Коротко

- Монолит прост, но склонен к связанности; модульный монолит добавляет строгие границы.
- Микросервисы дают независимость команд ценой распределённой сложности.
- Решающий фактор — организация и зрелость инфраструктуры, а не мода.
- Распределённый монолит — худший вариант.
- Фронтенду нужны агрегация данных, устойчивость к частичным отказам и терпимость к задержкам согласованности.
