Domain-Driven Design (Эрик Эванс, 2003) — подход к разработке сложных систем, в котором модель предметной области и язык бизнеса ставятся в центр проектирования. DDD — в первую очередь про бэкенд и про границы систем, но его идеи полезны и во фронтенде, особенно в больших продуктах и микрофронтендах.

## Стратегическое проектирование

### Ubiquitous Language — единый язык

Разработчики, аналитики и бизнес используют одни и те же термины — в разговорах, в задачах, **в коде**. Если бизнес говорит «бронь», а в коде `Reservation`, `Booking` и `Order` для одного понятия — модель уже расходится с реальностью.

```ts
// Язык бизнеса прямо в коде
export const confirmBooking = (booking: Booking, payment: Payment): ConfirmedBooking => { /* ... */ };
// а не: processData(obj, data2)
```

### Bounded Context — ограниченный контекст

Одно слово может значить разное в разных частях бизнеса. «Товар» в каталоге — описание, фото, характеристики; на складе — остаток и место хранения; в бухгалтерии — себестоимость и НДС. Пытаться сделать единую модель «Товара» для всех — путь к монстру.

**Bounded context** — граница, внутри которой модель и термины однозначны.

```text
┌─ Каталог ───────────┐   ┌─ Склад ─────────────┐   ┌─ Заказы ────────────┐
│ Product              │   │ StockItem           │   │ OrderLine           │
│  title, images,      │   │  sku, quantity,     │   │  productId, price,  │
│  attributes          │   │  location           │   │  quantity           │
└─────────────────────┘   └─────────────────────┘   └─────────────────────┘
```

Контексты общаются через явные контракты (API, события), а не через общие модели.

### Context Map

Карта отношений между контекстами: кто от кого зависит, кто чью модель переводит. Важный паттерн — **Anti-Corruption Layer**: слой перевода, защищающий вашу модель от чужой (на фронтенде — те же мапперы DTO из урока [Adapter](/tracks/patterns/adapter)).

## Тактическое проектирование

### Entity — сущность

Объект с **идентичностью**, которая сохраняется при изменении атрибутов. Пользователь остаётся тем же пользователем, сменив email.

### Value Object — объект-значение

Объект без идентичности, определяемый значениями; неизменяемый, сравнивается по содержимому:

```ts
export type Money = { readonly amount: number; readonly currency: 'RUB' | 'USD' };

export const money = (amount: number, currency: Money['currency']): Money => {
  if (!Number.isFinite(amount)) throw new Error('Некорректная сумма');
  return { amount: Math.round(amount * 100) / 100, currency };
};

export const add = (a: Money, b: Money): Money => {
  if (a.currency !== b.currency) throw new Error('Нельзя складывать разные валюты');
  return money(a.amount + b.amount, a.currency);
};
```

Value objects убирают «примитивную одержимость»: вместо `price: number` — `Money` с валютой и правилами. Брендированные типы TypeScript — лёгкий способ получить похожий эффект для идентификаторов ([Совместимость и branded types](/tracks/typescript/compatibility)).

### Aggregate — агрегат

Группа объектов, изменяемых как единое целое через **корень агрегата**, который охраняет инварианты:

```ts
export type Order = {
  readonly id: OrderId;
  readonly status: 'draft' | 'placed';
  readonly lines: readonly OrderLine[];
};

// Изменения только через функции корня, которые соблюдают правила
export function addLine(order: Order, line: OrderLine): Order {
  if (order.status !== 'draft') throw new Error('Нельзя менять оформленный заказ');
  if (order.lines.length >= 50) throw new Error('Не более 50 позиций');
  return { ...order, lines: [...order.lines, line] };
}
```

Снаружи нельзя «подправить» строку заказа в обход правил.

### Domain Events — доменные события

Факты, произошедшие в домене, в прошедшем времени: `OrderPlaced`, `PaymentFailed`. Связывают контексты и агрегаты без прямых вызовов. Во фронтенде близкая идея — actions NgRx, названные как события.

### Repository и Domain Service

- **Repository** — доступ к агрегатам как к коллекции (`findById`, `save`), скрывающий хранилище.
- **Domain Service** — логика, не принадлежащая одной сущности (перевод денег между счетами).

## DDD во фронтенде

- **Единый язык** в именах компонентов, сервисов, actions, маршрутов.
- **Bounded contexts → границы фич, библиотек Nx, микрофронтендов.** Команда «Каталога» владеет своей частью фронтенда так же, как бэкендом.
- **Value objects и брендированные типы** для денег, дат, идентификаторов.
- **Правила домена — чистые функции**, отделённые от компонентов.
- **Anti-corruption layer** — мапперы DTO на границе data-access.

> [!WARNING]
> DDD — не набор папок `entities/`, `value-objects/`, `aggregates/`. Без работы с экспертами предметной области и единого языка тактические паттерны превращаются в церемонию. Для простых CRUD-экранов DDD избыточен.

> [!INTERVIEW]
> «Что такое bounded context и как он связан с фронтендом?» — Граница, внутри которой модель предметной области и термины однозначны: «товар» в каталоге и на складе — разные модели с разными данными. Контексты общаются через явные контракты. Во фронтенде контексты становятся границами фич, библиотек и микрофронтендов: каждая владеет своими моделями и переводит чужие через мапперы (anti-corruption layer), а не разделяет одну общую модель на всё приложение.

## Коротко

- Стратегический DDD: единый язык, ограниченные контексты, карта контекстов.
- Тактический DDD: сущности, value objects, агрегаты, доменные события, репозитории.
- Value objects и branded types делают примитивы осмысленными.
- Контексты → границы фич, библиотек, микрофронтендов и команд.
- DDD нужен для сложных доменов, а не для каждого CRUD.
