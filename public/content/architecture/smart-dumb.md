Разделение компонентов на **smart** (контейнеры) и **presentational** (презентационные, «глупые») — самый практичный архитектурный приём в Angular. Он отвечает на вопрос, где должна жить логика, а где — только отображение.

## Два вида компонентов

| | Smart (container) | Presentational (dumb, UI) |
| --- | --- | --- |
| Знает о | сервисах, сторах, роутере, API | только своих inputs |
| Получает данные | через `inject()` | через `input()` |
| Сообщает о событиях | вызывает сервисы/фасады | через `output()` |
| Состояние | бизнес-состояние фичи | только локальное UI (открыт ли дропдаун) |
| Переиспользуемость | низкая, привязан к фиче | высокая |
| Тестирование | с моками сервисов | просто: inputs → DOM, клик → output |
| Обычно это | страницы, маршрутизируемые компоненты | карточки, списки, формы, кнопки |

## Пример

```ts
// Presentational: ничего не знает о том, откуда данные
@Component({
  selector: 'app-product-card',
  imports: [CurrencyPipe],
  template: `
    <article>
      <img [src]="product().image" [alt]="product().title" />
      <h3>{{ product().title }}</h3>
      <p>{{ product().price | currency: 'RUB' }}</p>
      <button (click)="addToCart.emit(product().id)" [disabled]="inCart()">
        {{ inCart() ? 'В корзине' : 'В корзину' }}
      </button>
    </article>
  `,
})
export class ProductCard {
  readonly product = input.required<Product>();
  readonly inCart = input(false);
  readonly addToCart = output<string>();
}

// Smart: связывает данные и действия
@Component({
  selector: 'app-catalog-page',
  imports: [ProductCard],
  template: `
    @for (product of catalog.products(); track product.id) {
      <app-product-card
        [product]="product"
        [inCart]="cart.has(product.id)"
        (addToCart)="cart.add($event)"
      />
    }
  `,
})
export class CatalogPage {
  protected readonly catalog = inject(CatalogFacade);
  protected readonly cart = inject(CartFacade);
}
```

`ProductCard` можно использовать в каталоге, в рекомендациях, в избранном и в Storybook — он зависит только от своих inputs.

## Поток данных

```text
          ┌──────────── Smart (страница) ◀── фасад / стор / сервисы
 inputs ▼ │ ▲ outputs
    Presentational
      inputs ▼ ▲ outputs
        Presentational
```

Данные спускаются вниз через inputs, события поднимаются вверх через outputs. Состояние меняется в одном месте — легко понять, почему UI выглядит так, как выглядит.

## Фасад для smart-компонентов

Smart-компоненту удобно общаться не с десятком сервисов, а с одним [фасадом](/tracks/patterns/facade) фичи: состояние — сигналы, действия — методы.

## Правила, которые помогают

- Презентационный компонент **не внедряет** сервисы данных (исключение — чисто UI-сервисы: `FocusMonitor`, `Overlay`, локализация).
- Презентационный компонент **не мутирует** входные данные — только сообщает о намерении через output.
- Smart-компонентов мало (страницы, крупные блоки фичи), презентационных — много.
- Название подсказывает роль: `*Page`, `*Container` — умные; `*Card`, `*List`, `*Form` — презентационные.
- Презентационные компоненты, нужные нескольким фичам, переезжают в библиотеку `ui` (в Nx — тип `ui`).

## Не доводите до абсурда

- Пробрасывать данные через 4–5 уровней ради «чистоты» (prop drilling) хуже, чем внедрить фасад во вложенный компонент фичи.
- Форма с локальным состоянием и валидацией может держать это состояние в себе — это UI-состояние.
- Деление не обязано быть бинарным: компонент может быть «умным» внутри фичи и при этом не знать об HTTP (работать через фасад).

## Ещё одна польза: OnPush

Презентационный компонент с сигнальными inputs и без внешнего состояния — идеальный кандидат для `OnPush` (который в Angular 22 и так по умолчанию): он перерисовывается только при новых inputs или своих событиях.

> [!INTERVIEW]
> «Зачем делить компоненты на smart и presentational?» — Чтобы отделить «откуда данные и что делать» от «как показать». Презентационные компоненты получают данные через inputs и сообщают о действиях через outputs: их легко переиспользовать, тестировать и показывать в Storybook. Умные компоненты (обычно страницы) внедряют фасады и сервисы, связывают данные с презентационными компонентами и обрабатывают события. Поток данных однонаправленный и предсказуемый.

## Коротко

- Smart: `inject()` фасадов и сервисов, связывание, обработка событий.
- Presentational: только `input()`/`output()`, переиспользуемый и простой в тестах.
- Данные вниз, события вверх.
- Фасад упрощает smart-компоненты.
- Без фанатизма: избегайте глубокого prop drilling.
