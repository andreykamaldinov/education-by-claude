Распределённые системы ломаются по-другому, чем монолиты: сеть теряет сообщения, сервисы недоступны, транзакции не охватывают несколько баз. Для этих проблем сложились устойчивые паттерны. Даже работая на фронтенде, полезно их знать: они объясняют поведение API и влияют на UX.

## Database per Service

У каждого сервиса **своя** база данных, недоступная другим напрямую. Другие сервисы получают данные только через API или события.

- Плюсы: независимые схемы и релизы, выбор хранилища под задачу.
- Минусы: нет JOIN между сервисами, нет общих транзакций, данные дублируются.

## Saga — распределённая транзакция

Как оформить заказ, если резерв товара, оплата и создание доставки — в разных сервисах? Двухфазный коммит (2PC) плохо масштабируется и связывает сервисы. **Saga** — последовательность локальных транзакций, где у каждого шага есть **компенсирующее действие**.

```text
Создать заказ → Зарезервировать товар → Списать оплату → Создать доставку
       ↑                ↑                     ✗ ошибка
       │                └─ Снять резерв ◀─────┘ (компенсация)
       └─ Отменить заказ ◀─────────────────────┘
```

Два стиля:

- **Хореография** — сервисы реагируют на события друг друга (`OrderCreated` → склад резервирует → `StockReserved` → оплата…). Просто начать, трудно увидеть процесс целиком.
- **Оркестрация** — отдельный оркестратор (сервис или движок вроде Temporal, Camunda) явно управляет шагами и компенсациями. Процесс виден, но оркестратор — ещё один компонент.

Для фронтенда: оформление заказа может вернуть `202 Accepted` и статус `pending`, а итог — прийти позже. UI показывает состояние процесса («Ожидаем подтверждения оплаты»), а не мгновенный успех.

## Transactional Outbox

Проблема: сервис сохраняет заказ в БД и публикует событие в брокер. Если упасть между этими действиями, событие потеряется (или опубликуется для несохранённого заказа).

Решение: в **той же транзакции**, что и изменение данных, записать событие в таблицу `outbox`. Отдельный процесс читает outbox и публикует события в брокер.

```text
BEGIN
  INSERT INTO orders ...
  INSERT INTO outbox (event) VALUES ('OrderPlaced ...')
COMMIT
        ↓ (relay / CDC, например Debezium)
     брокер сообщений
```

Гарантия: событие опубликуется **хотя бы один раз** (at-least-once). Отсюда следующий паттерн.

## Идемпотентность

При at-least-once доставке и автоматических повторах сообщение или запрос может прийти дважды. Обработчик должен давать тот же результат при повторе.

```http
POST /api/payments
Idempotency-Key: 6f1c2a9e-1b7d-4f0a-9a51-3c2e1d8b7f40
```

Сервер запоминает ключ и при повторе возвращает сохранённый результат вместо повторного списания. Фронтенд генерирует ключ один раз на действие пользователя (`crypto.randomUUID()`) и использует его при повторах — тогда retry безопасен даже для POST.

## Circuit Breaker — автоматический выключатель

Если сервис-зависимость падает, бесконечные запросы к нему только усугубляют ситуацию (исчерпание потоков, каскадный отказ). Circuit breaker отслеживает ошибки и «размыкает цепь»:

```text
CLOSED ──(ошибок больше порога)──▶ OPEN ──(таймаут)──▶ HALF-OPEN
  ▲                                   │                      │
  └──────────(пробные запросы успешны)┘◀─────────────────────┘
                                       (ошибка → снова OPEN)
```

- **Closed** — запросы идут как обычно, ошибки считаются.
- **Open** — запросы сразу завершаются ошибкой (или fallback) без обращения к сервису.
- **Half-open** — пропускаются пробные запросы; успех закрывает цепь.

Тот же принцип полезен и на клиенте: если API рекомендаций постоянно падает, перестаньте его опрашивать на время и покажите страницу без блока рекомендаций.

## Retry с backoff и jitter

Повторять — да, но с **экспоненциальной задержкой** и **случайным разбросом** (jitter), иначе тысячи клиентов одновременно «добьют» восстанавливающийся сервис (thundering herd).

```ts
retry({
  count: 4,
  delay: (_error, attempt) => timer(Math.min(30_000, 2 ** attempt * 300) * (0.5 + Math.random())),
});
```

Повторяйте только временные ошибки (сеть, 502/503/504, 429 с `Retry-After`) и только идемпотентные операции.

## Bulkhead — переборки

Изолировать ресурсы так, чтобы отказ одной части не затопил остальные: отдельные пулы соединений/потоков для разных зависимостей. Во фронтенде аналог — изолированные блоки страницы с отдельными состояниями ошибок и `@defer`-блоками: упал виджет — страница жива.

## Timeout

Каждый сетевой вызов должен иметь таймаут. «Вечное ожидание» хуже быстрой ошибки: оно держит ресурсы и пользователя.

## Strangler Fig — постепенная миграция

Как перейти с монолита на сервисы (или со старого фронтенда на новый) без «большого переписывания»: новые части строятся рядом, прокси/роутинг постепенно перенаправляет на них трафик, старый код «отмирает» по частям. Для фронтенда это миграция AngularJS → Angular по маршрутам или вынос разделов в микрофронтенды.

> [!INTERVIEW]
> «Как обеспечить согласованность данных между микросервисами без распределённых транзакций?» — Паттерном Saga: процесс разбивается на локальные транзакции в каждом сервисе, а при ошибке выполняются компенсирующие действия (снять резерв, вернуть деньги). Координация — хореографией через события или оркестратором. Для надёжной публикации событий вместе с изменением данных — Transactional Outbox, а обработчики делают идемпотентными, потому что доставка — «хотя бы один раз».

## Коротко

- Database per Service: свои данные, доступ только через API и события.
- Saga: локальные транзакции + компенсации; хореография или оркестрация.
- Outbox: событие сохраняется в той же транзакции, публикуется отдельно.
- Идемпотентность и `Idempotency-Key` делают повторы безопасными.
- Circuit breaker, retry с backoff и jitter, bulkhead, timeout — защита от каскадных отказов.
