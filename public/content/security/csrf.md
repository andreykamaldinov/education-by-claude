CSRF (Cross-Site Request Forgery) — подделка межсайтового запроса. Злоумышленник заставляет браузер пользователя отправить запрос на ваш сайт, и браузер **автоматически прикладывает cookies** пользователя. Если сервер аутентифицирует по cookie и не проверяет происхождение запроса — действие выполнится от имени жертвы.

## Как работает атака

1. Пользователь вошёл на `bank.example`, сессия — в cookie.
2. Он открывает `evil.example`, где спрятана форма:

```html
<form action="https://bank.example/api/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="100000" />
</form>
<script>document.getElementById('f').submit();</script>
```

3. Браузер отправляет POST на `bank.example` вместе с сессионной cookie.
4. Сервер видит валидную сессию и выполняет перевод.

Злоумышленник **не может прочитать ответ** (это запрещает Same-Origin Policy), но ему это и не нужно — действие уже совершено.

## Условия уязвимости

- Аутентификация по cookie (или по другим данным, которые браузер прикладывает сам: HTTP Basic, клиентские сертификаты).
- Запрос с побочным эффектом, который можно сформировать без знания секрета.
- Нет проверки происхождения запроса.

Если API аутентифицируется **только** заголовком `Authorization: Bearer ...`, который фронтенд добавляет вручную, классический CSRF невозможен — чужой сайт не может добавить этот заголовок. Но у такого подхода другие риски (хранение токена в JS — см. [Где хранить токены](/tracks/security/token-storage)).

## Защита 1: SameSite cookies

```http
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax
```

| Значение | Когда cookie отправляется с запросом с другого сайта |
| --- | --- |
| `Strict` | никогда (даже при переходе по ссылке — пользователь придёт «разлогиненным») |
| `Lax` | только при навигации верхнего уровня методом GET (клик по ссылке) |
| `None` | всегда (обязателен `Secure`) — для встраиваемых виджетов и SSO |

Современные браузеры считают cookie без атрибута `SameSite` как `Lax`. Это закрывает большинство CSRF-атак через POST, но:

- «сайт» в терминах SameSite — это регистрируемый домен: `evil.example.com` и `app.example.com` — **один сайт**, поддомены могут атаковать друг друга;
- `GET` с побочными эффектами по-прежнему уязвим при `Lax`;
- для `SameSite=None` нужна отдельная защита.

## Защита 2: CSRF-токен

Сервер выдаёт случайный токен, который клиент обязан отправить в запросе так, как чужой сайт не может: в заголовке или теле, прочитав его из места, доступного только вашему origin.

### Double submit cookie и Angular

`HttpClient` реализует этот паттерн из коробки:

1. Сервер ставит **читаемую из JS** cookie `XSRF-TOKEN` со случайным значением.
2. `HttpClient` при мутирующих запросах (POST, PUT, PATCH, DELETE) **на относительные URL того же origin** читает cookie и добавляет заголовок `X-XSRF-TOKEN`.
3. Сервер сверяет заголовок с cookie (или со значением в сессии).

Чужой сайт не может прочитать cookie вашего домена и, следовательно, не может поставить правильный заголовок.

```ts
provideHttpClient(
  withXsrfConfiguration({
    cookieName: 'XSRF-TOKEN', // значения по умолчанию
    headerName: 'X-XSRF-TOKEN',
  }),
);
// отключить: withNoXsrfProtection()
```

> [!WARNING]
> Angular **не добавляет** XSRF-заголовок к абсолютным URL и к GET-запросам. Если API на другом домене (`https://api.example.com`), встроенная защита не сработает — нужен свой интерсептор или другая схема. И это механизм клиента: проверку обязан делать сервер.

### Synchronizer token

Классическая серверная схема: токен хранится в сессии и вставляется в HTML формы; сервер сверяет значение из формы с сессией.

## Защита 3: проверка Origin

Браузер добавляет заголовок `Origin` к POST-запросам (и `Sec-Fetch-Site: cross-site` в современных браузерах). Сервер может отклонять мутирующие запросы с чужим origin:

```text
Origin: https://evil.example        → 403
Sec-Fetch-Site: cross-site          → 403 для мутаций
```

## Защита 4: правильные методы

GET не должен менять состояние. Иначе `<img src="https://bank.example/api/delete-account">` в любом форуме удалит аккаунт.

## Чек-лист

- [ ] Сессионные cookies: `HttpOnly; Secure; SameSite=Lax` (или `Strict`).
- [ ] Мутации только через POST/PUT/PATCH/DELETE.
- [ ] CSRF-токен (встроенная XSRF-защита `HttpClient` + проверка на сервере).
- [ ] Сервер проверяет `Origin` / `Sec-Fetch-Site` для мутаций.
- [ ] CORS настроен строго (не `*` с credentials) — см. [CORS](/tracks/security/cors).
- [ ] Нет XSS: при XSS злоумышленник обойдёт любую CSRF-защиту, потому что код выполняется на вашем origin.

> [!INTERVIEW]
> «Что такое CSRF и как Angular помогает защититься?» — Атака, при которой чужой сайт заставляет браузер жертвы отправить запрос на ваш сервер с её cookies. Защита: `SameSite`-cookies, CSRF-токены, проверка `Origin`, отсутствие побочных эффектов у GET. `HttpClient` реализует double-submit-cookie: читает cookie `XSRF-TOKEN` и отправляет её значение в заголовке `X-XSRF-TOKEN` для мутирующих запросов на свой origin; сервер сверяет значения. Чужой сайт не может прочитать cookie и подставить заголовок.

## Коротко

- CSRF эксплуатирует автоматическую отправку cookies браузером.
- `SameSite=Lax/Strict` закрывает большинство сценариев, но не поддомены и GET-мутации.
- `HttpClient` добавляет `X-XSRF-TOKEN` из cookie `XSRF-TOKEN` для мутаций на свой origin.
- Сервер проверяет токен и `Origin`.
- XSS обходит любую CSRF-защиту.
