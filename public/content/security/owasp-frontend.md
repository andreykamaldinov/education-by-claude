OWASP Top 10 — рейтинг самых критичных рисков безопасности веб-приложений, который обновляется раз в несколько лет (актуальная редакция — 2025). Большинство пунктов относятся к серверу, но фронтенд-разработчик влияет на многие из них. Ниже — список глазами Angular-разработчика.

## A01. Broken Access Control — нарушение контроля доступа

Пользователь получает доступ к чужим данным или функциям: подменил id в URL, вызвал API админки, изменил роль в токене.

Во фронтенде:

- Guards в роутере и скрытие кнопок по ролям — это **UX, а не защита**. Сервер проверяет права на каждый запрос.
- Не полагайтесь на id из URL как на доказательство владения: `/orders/42` должен возвращать 403, если заказ чужой.
- Не отдавайте с сервера лишние данные «потому что клиент всё равно не покажет».

## A02. Security Misconfiguration — небезопасная конфигурация

- Отсутствуют security-заголовки (CSP, HSTS, `frame-ancestors`) — см. [Security-заголовки](/tracks/security/clickjacking-headers).
- Source maps production-сборки публично доступны и раскрывают исходники и комментарии.
- Dev-режим или отладочные флаги в продакшене.
- CORS с `*` и credentials, отражение любого Origin.
- Ключи API в `environment.ts` — они попадают в бандл и видны всем.

> [!WARNING]
> Всё, что есть в бандле Angular-приложения, публично. «Секретный» ключ в `environment.prod.ts` — не секрет. Секреты живут только на сервере; браузеру отдаются публичные ключи с ограничениями (по домену, по квоте).

## A03. Software Supply Chain Failures — уязвимости цепочки поставок

Уязвимые или вредоносные зависимости npm, скомпрометированные CDN, захваченные пакеты. См. [Безопасность зависимостей](/tracks/security/supply-chain).

## A04. Cryptographic Failures — криптографические ошибки

- Данные без HTTPS, смешанный контент.
- Самодельное «шифрование» на клиенте (base64 — не шифрование).
- Персональные данные в `localStorage` без необходимости.
- Использование `Math.random()` для токенов и идентификаторов — нужен `crypto.getRandomValues()` или `crypto.randomUUID()`.

## A05. Injection — внедрение

Для фронтенда главное — **XSS** (входит в эту категорию): `innerHTML`, `bypassSecurityTrust*`, сборка шаблонов из данных, `javascript:`-URL. См. [XSS](/tracks/security/xss). Также — внедрение в запросы через небезопасное построение URL:

```ts
// Плохо: пользователь может передать '../admin' или '?role=admin&'
this.http.get(`/api/users/${userInput}`);

// Лучше: кодировать сегмент и проверять формат
this.http.get(`/api/users/${encodeURIComponent(userId)}`);
```

## A06. Insecure Design — небезопасный дизайн

Уязвимость в самой логике: восстановление пароля по «секретному вопросу», отсутствие лимита попыток, бизнес-правила только на клиенте (скидка считается в браузере и отправляется на сервер).

```ts
// Плохо: сервер верит цене от клиента
this.api.checkout({ items, total: this.total() });

// Хорошо: клиент отправляет только что купить, цену считает сервер
this.api.checkout({ items: items.map(({ id, qty }) => ({ id, qty })) });
```

## A07. Authentication Failures — ошибки аутентификации

- Слабые требования к паролям, нет поддержки менеджеров паролей (запрет вставки в поле пароля — антипаттерн).
- Сессии без истечения, токены без ротации.
- Сообщения вида «пользователь не найден» / «неверный пароль» по отдельности раскрывают существование аккаунтов.

Во фронтенде: правильные `autocomplete`-атрибуты (`username`, `current-password`, `new-password`, `one-time-code`), поддержка passkeys, корректная очистка состояния при выходе. См. [JWT, OAuth, PKCE](/tracks/security/auth).

## A08. Software or Data Integrity Failures — нарушение целостности

- Скрипты с CDN без Subresource Integrity.
- Автообновления без проверки подписи.
- Десериализация недоверенных данных: доверие к JSON из `postMessage` без проверки `event.origin`.

```ts
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://payments.example.com') return; // обязательно
  if (!isPaymentResult(event.data)) return; // проверка формы
  this.handlePayment(event.data);
});
```

## A09. Logging & Alerting Failures — недостаточный мониторинг

Фронтенд тоже должен сообщать о проблемах: ошибки JS (Sentry и аналоги), нарушения CSP (`report-to`), аномалии. Но **без** токенов, паролей и персональных данных в логах.

## A10. Mishandling of Exceptional Conditions — некорректная обработка исключений

Новая категория 2025 года: приложение в нештатной ситуации ведёт себя небезопасно — раскрывает стек-трейсы и внутренние детали в сообщениях об ошибках, «открывается» при сбое проверки (fail open) вместо отказа, оставляет систему в неконсистентном состоянии.

Во фронтенде: не показывайте пользователю сырой текст серверной ошибки, обрабатывайте ошибки в интерсепторе единообразно, не считайте «нет ответа от сервиса прав» разрешением.

## Чек-лист Angular-проекта

- [ ] Нет `bypassSecurityTrust*` без обоснования; нет `nativeElement.innerHTML`.
- [ ] CSP без `unsafe-inline` для скриптов; Trusted Types по возможности.
- [ ] Токены — по выбранной стратегии ([Где хранить токены](/tracks/security/token-storage)); интерсептор добавляет их только своим API.
- [ ] XSRF-защита включена и проверяется сервером.
- [ ] В бандле нет секретов; source maps не публичны.
- [ ] `npm audit` в CI, lock-файл в репозитории, обновления зависимостей.
- [ ] `postMessage` — проверка `origin` и данных.
- [ ] Права проверяет сервер; клиент отправляет намерения, а не вычисленные цены и роли.

> [!INTERVIEW]
> «Какие уязвимости из OWASP Top 10 касаются фронтенда?» — Прежде всего XSS (инъекции): Angular защищает по умолчанию, но защиту можно обойти. Нарушение контроля доступа: guards и скрытие кнопок — не защита, проверяет сервер. Небезопасная конфигурация: CSP и заголовки, секреты в бандле, открытые source maps. Цепочка поставок: уязвимые npm-зависимости. Ошибки аутентификации и хранения токенов, отсутствие проверки `origin` в `postMessage`, бизнес-логика только на клиенте.

## Коротко

- Клиентские проверки — UX; доступ, цены и роли проверяет сервер.
- Всё в бандле публично — секретов там быть не должно.
- XSS — главная фронтенд-инъекция; CSP и Trusted Types — второй рубеж.
- Зависимости — тоже поверхность атаки.
- Обработка ошибок не должна раскрывать детали и «открывать» доступ при сбое.
