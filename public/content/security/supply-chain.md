Типичное Angular-приложение тянет сотни транзитивных npm-пакетов. Каждый из них выполняется у вас при установке (`postinstall`-скрипты), при сборке и в браузере пользователей. Атака на цепочку поставок — внедрение вредоносного кода через одну из этих зависимостей — одна из самых опасных и быстро растущих угроз.

## Как это происходит

| Сценарий | Пример |
| --- | --- |
| Захват аккаунта мейнтейнера | злоумышленник публикует новую версию популярного пакета с вредоносным кодом |
| Самораспространяющийся червь | вредоносный пакет крадёт npm-токены с машин разработчиков и публикует заражённые версии их пакетов |
| Typosquatting | пакет `angluar-core` или `rxjs-utils` вместо настоящего |
| Dependency confusion | публичный пакет с именем вашего внутреннего пакета и более высокой версией |
| Протестное ПО | автор намеренно добавляет разрушительный код в свой пакет |
| Компрометация CDN | изменённый скрипт на стороннем CDN |

Вредоносный код обычно крадёт переменные окружения и токены (npm, GitHub, облака) на машинах разработчиков и в CI, кошельки, или внедряет код в собранный бандл.

## Lock-файл

```bash
npm ci   # установка строго по package-lock.json, ошибка при расхождении с package.json
```

- `package-lock.json` фиксирует точные версии и **хеши** (`integrity`) всего дерева зависимостей. Обязательно коммитьте его.
- В CI используйте `npm ci`, а не `npm install`.
- Диапазон `^1.2.3` в `package.json` разрешает автоматически получить новую (возможно, заражённую) минорную версию при обновлении lock-файла.

## Аудит уязвимостей

```bash
npm audit                     # известные уязвимости в дереве
npm audit --omit=dev          # только то, что попадает в продакшен
npm audit fix                 # обновить в пределах semver-диапазонов
npm ls vulnerable-package     # откуда тянется пакет
```

Добавьте аудит в CI и разбирайте результаты: не каждая уязвимость эксплуатируема в вашем контексте (например, уязвимость dev-сервера не попадает в продакшен), но каждая требует решения.

`overrides` в `package.json` позволяет принудительно поднять версию транзитивной зависимости:

```json
{
  "overrides": {
    "vulnerable-lib": "^2.4.1"
  }
}
```

## Автоматические обновления

Renovate или Dependabot создают pull request-ы на обновления. Это уменьшает «долг» обновлений — чем дольше не обновляешься, тем больнее и опаснее. Хорошая практика:

- группировать обновления (весь `@angular/*` — одним PR);
- автоматически мержить только патчи после зелёного CI;
- **задержка перед обновлением** на свежие версии (например, 3–7 дней): большинство вредоносных публикаций обнаруживают и удаляют за первые часы и дни. В pnpm (с версии 10.16) это настройка `minimumReleaseAge`, в Renovate — опция `minimumReleaseAge`; в npm похожая настройка появляется в свежих версиях npm 11 — сверьтесь с документацией вашей версии.

## Скрипты установки

`preinstall`/`postinstall`-скрипты выполняются автоматически с правами пользователя. Варианты защиты:

```bash
npm ci --ignore-scripts              # отключить скрипты установки
npm config set ignore-scripts true   # глобально
```

Альтернативные менеджеры пакетов (pnpm, Bun) по умолчанию не выполняют скрипты зависимостей без явного разрешения. Пакеты, которым скрипты действительно нужны (например, нативные бинарники), добавляются в белый список.

## Меньше зависимостей

Лучшая зависимость — та, которой нет:

- Нужна функция из десяти строк? Напишите её.
- Перед добавлением пакета проверьте: кто мейнтейнер, сколько у пакета собственных зависимостей, когда последний релиз, есть ли `provenance`.
- Используйте платформу: `structuredClone` вместо `lodash.clonedeep`, `Intl` вместо библиотек форматирования, `fetch` вместо HTTP-клиентов, сигналы Angular вместо отдельной библиотеки состояния для простых случаев.

## Provenance и подписи

npm поддерживает **provenance**: пакет, опубликованный из CI (GitHub Actions и др.), содержит подписанную аттестацию — из какого репозитория и коммита он собран.

```bash
npm audit signatures   # проверить подписи и аттестации установленных пакетов
```

Публикуя свои пакеты, используйте trusted publishing (публикация из CI без долгоживущих npm-токенов) и двухфакторную аутентификацию.

## Внешние скрипты: Subresource Integrity

Если подключаете скрипт с CDN, укажите хеш — браузер откажется выполнять изменённый файл:

```html
<script
  src="https://cdn.example.com/lib@3.2.1/lib.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>
```

Angular CLI умеет добавлять SRI к своим бандлам: `"subresourceIntegrity": true` в `angular.json`.

## Секреты на машине разработчика и в CI

- Не храните долгоживущие токены в `.npmrc` и переменных окружения CI шире необходимого.
- Разделяйте права: шаг установки зависимостей не должен иметь доступа к секретам деплоя.
- Включайте 2FA для npm и GitHub.

> [!INTERVIEW]
> «Как защитить проект от уязвимых и вредоносных зависимостей?» — Фиксировать дерево lock-файлом и ставить через `npm ci`; регулярно запускать `npm audit` в CI; обновляться небольшими шагами через Renovate/Dependabot с задержкой на свежие релизы; отключать install-скрипты или разрешать их точечно; минимизировать число зависимостей; проверять provenance; для внешних скриптов — SRI; ограничивать доступ к секретам в CI.

## Коротко

- Каждая зависимость выполняет код у вас и у пользователей.
- Lock-файл + `npm ci` + `npm audit` в CI — минимум.
- Обновляйтесь регулярно, но с задержкой на свежие версии.
- `--ignore-scripts`, меньше зависимостей, проверка мейнтейнеров и provenance.
- SRI для внешних скриптов, 2FA и узкие права для токенов.
