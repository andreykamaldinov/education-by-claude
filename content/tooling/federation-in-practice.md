Настроить федерацию по туториалу — день работы. Сделать так, чтобы десять команд годами выкатывали микрофронтенды без поломок, — задача архитектуры. Этот урок о практических проблемах и проверенных решениях.

## 1. Версии shared-зависимостей

Самая частая проблема: shell собран с Angular 22.1, а remote — с 22.2 или, хуже, 21.x.

- **Angular и RxJS — singleton, одна мажорная версия во всей системе.** Обновление мажорной версии Angular — скоординированный процесс для всех команд.
- `strictVersion: true` — лучше явная ошибка при загрузке, чем тонкие баги от несовместимости.
- Монорепозиторий (Nx) с единым `package.json` снимает большую часть проблем версионирования: все собираются с одними версиями.
- В polyrepo — общий «платформенный» пакет с версиями и автоматические обновления (Renovate) во всех репозиториях.

```text
Ошибка «NG0203: inject() must be called from an injection context» или «NullInjectorError» в remote —
частый признак того, что на странице оказалось два экземпляра @angular/core.
```

## 2. Контракты между частями

Exposed-модули remote-а — **публичный API**, как REST-эндпоинт:

```ts
// libs/contracts/catalog.ts — общий пакет контрактов
export type CatalogRemote = {
  CATALOG_ROUTES: Routes;
};

export type CartChangedEvent = CustomEvent<{ count: number; total: number }>;
export const CART_CHANGED = 'shop:cart-changed' as const;
```

```ts
// shell: типизированная загрузка
loadRemoteModule<CatalogRemote>('catalog', './Routes').then((m) => m.CATALOG_ROUTES);
```

- Изменения контрактов — только обратно совместимые, удаление — через депрекейт.
- Контрактные тесты: shell проверяет, что remote экспортирует ожидаемое; события проверяются по схеме.

## 3. Коммуникация

От предпочтительного к нежелательному:

1. **URL** — маршрут и query-параметры. Сохраняются при перезагрузке, шарятся ссылкой.
2. **Браузерные события** с типизированными контрактами (`CustomEvent`, `BroadcastChannel`).
3. **Общий сервис** из shared-библиотеки — singleton через федерацию (пользователь, тема, локаль). Только для действительно сквозных вещей.
4. **Общий стор** со всем состоянием — возвращает связанность монолита. Избегайте.

## 4. Аутентификация

Shell отвечает за вход и хранение сессии. Remote-ы получают пользователя через общий `AuthFacade` из shared-библиотеки или через токен, а HTTP-интерсепторы для API живут в shared-библиотеке, чтобы каждый remote не реализовывал их заново.

## 5. Роутинг

- Shell владеет корневыми маршрутами (`/catalog/**` → remote catalog), remote — своими дочерними.
- Ссылки между микрофронтендами — абсолютные пути (`/cart`), не знание внутренних маршрутов соседа.
- Remote должен уметь работать и отдельно (standalone-режим для разработки), и внутри shell.

## 6. Стили и дизайн-система

- Общая библиотека компонентов и дизайн-токенов (CSS-переменные) — иначе пять оттенков «основной кнопки».
- Инкапсуляция стилей Angular защищает компоненты, но глобальные стили remote-ов могут конфликтовать: префиксы, CSS layers, запрет глобальных селекторов в remote-ах.
- Shared-версия дизайн-системы — singleton, как Angular.

## 7. Устойчивость

Remote может быть недоступен (деплой, сбой CDN, ошибка в новой версии):

```ts
{
  path: 'recommendations',
  loadComponent: () =>
    loadRemoteModule('recommendations', './Widget')
      .then((m) => m.RecommendationsWidget)
      .catch(() => import('./fallbacks/unavailable').then((m) => m.UnavailableWidget)),
}
```

- Fallback-компоненты для недоступных частей.
- Мониторинг ошибок загрузки remote-ов.
- Shell не должен «падать целиком» из-за одного remote-а.

## 8. Деплой и версии remote-ов

- Каждый remote деплоится независимо по своему URL; shell читает адреса из манифеста.
- Манифест — точка управления: откатить remote = поменять URL в манифесте на предыдущую версию.
- Кеширование: `remoteEntry.json` (или `.js`) и манифест — `no-cache`, чанки с хешами — `immutable`.
- Канареечные релизы — разные манифесты для части пользователей.

## 9. Производительность

- Следите, чтобы shared-зависимости действительно были общими — анализируйте сетевые запросы на дубли.
- `skip` для ненужных точек входа пакетов в Native Federation.
- Предзагрузка remote-ов, на которые пользователь вероятно перейдёт.
- Не делайте слишком мелких remote-ов: каждый — это запросы, манифест, накладные расходы.

## 10. Разработка и тестирование

- Локально: shell + один remote из исходников, остальные — с dev-стенда (манифест для разработки).
- E2E на собранной системе в staging-окружении.
- Nx: генераторы host/remote, `nx serve shell --devRemotes=catalog` поднимает нужные remote-ы.

> [!INTERVIEW]
> «С какими проблемами вы столкнётесь при внедрении микрофронтендов?» — Версии shared-зависимостей (Angular и RxJS должны быть singleton одной версии, иначе два экземпляра фреймворка), контракты и коммуникация между частями (URL и типизированные события вместо общего стора), единая аутентификация и дизайн-система, конфликты глобальных стилей, устойчивость к недоступности remote-а (fallback), стратегия деплоя и кеширования манифеста, дублирование зависимостей в бандлах и интеграционное тестирование.

## Коротко

- Angular/RxJS/дизайн-система — singleton одной версии; монорепозиторий упрощает это.
- Exposed-модули и события — публичные контракты: типизируйте и версионируйте.
- Коммуникация через URL и события; общий стор — антипаттерн.
- Fallback для недоступных remote-ов, манифест как точка отката.
- Следите за дублированием зависимостей и тестируйте систему целиком.
