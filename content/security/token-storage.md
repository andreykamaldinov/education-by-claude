«Где хранить JWT во фронтенде?» — вопрос без идеального ответа, и именно поэтому его любят на собеседованиях. Каждый вариант защищает от одного и открывает другое. Разберём компромиссы.

## Модель угроз

Две главные угрозы для токенов в браузере:

- **XSS** — чужой скрипт выполняется на вашей странице и может прочитать всё, что доступно JavaScript, и отправить запросы от имени пользователя.
- **CSRF** — чужой сайт заставляет браузер отправить запрос с автоматически приложенными cookies.

## Вариант 1: localStorage / sessionStorage

```ts
localStorage.setItem('access_token', token);
// интерсептор: Authorization: Bearer <token>
```

| Плюсы | Минусы |
| --- | --- |
| просто | **любой XSS читает токен** и может использовать его где угодно, даже после закрытия вкладки |
| нет CSRF (токен добавляется вручную) | refresh-токен в localStorage — долгоживущий секрет, доступный JS |
| работает с API на других доменах | токен переживает закрытие браузера |

## Вариант 2: память JavaScript

```ts
@Injectable({ providedIn: 'root' })
export class AuthStore {
  private readonly accessToken = signal<string | null>(null); // только в памяти
}
```

| Плюсы | Минусы |
| --- | --- |
| XSS не может «унести» токен из хранилища одним `localStorage.getItem` | при перезагрузке страницы токен теряется — нужен способ его восстановить |
| | XSS всё равно может вызывать API через ваш же код, пока вкладка открыта |

Обычно комбинируется с refresh-токеном в `HttpOnly`-cookie: при загрузке приложения выполняется «тихий» запрос `/auth/refresh`, cookie уходит автоматически, сервер возвращает новый access-токен в память.

## Вариант 3: HttpOnly cookie

```http
Set-Cookie: __Host-access=eyJ...; Path=/; Secure; HttpOnly; SameSite=Strict
```

| Плюсы | Минусы |
| --- | --- |
| JavaScript не может прочитать токен — XSS не украдёт его | нужна защита от CSRF (SameSite + XSRF-токен) |
| браузер управляет отправкой | сложнее с API на другом сайте (нужен `SameSite=None` и CORS с credentials) |

## Вариант 4: BFF (Backend for Frontend)

```text
Браузер ──cookie сессии (HttpOnly)──▶ BFF (ваш сервер) ──access token──▶ API
                                       │
                                       └── хранит токены, выполняет OAuth-поток и refresh
```

- Токены **никогда не попадают в браузер**.
- BFF — конфиденциальный OAuth-клиент (с client secret), может использовать более строгие механизмы.
- Браузер общается с BFF на том же origin: нет CORS, cookie `SameSite=Strict`.

Это подход, рекомендуемый актуальными рекомендациями IETF по безопасности браузерных OAuth-приложений для систем с высокими требованиями (банки, медицина, админки).

## Сравнение

| | localStorage | память + refresh в cookie | HttpOnly cookie | BFF |
| --- | --- | --- | --- | --- |
| Кража токена при XSS | да | access — только пока открыта вкладка | нет | нет |
| Действия от имени пользователя при XSS | да | да | да | да |
| CSRF | нет | на refresh-эндпоинт — нужна защита | нужна защита | нужна защита |
| Сложность | низкая | средняя | средняя | высокая (нужен сервер) |

> [!NOTE]
> Ни один вариант не защищает от XSS полностью: если чужой код выполняется на вашей странице, он может отправлять запросы от имени пользователя, пока тот на сайте. Хранилище токена определяет лишь, может ли злоумышленник **унести** доступ и использовать его потом. Поэтому главная защита — отсутствие XSS (санитизация, CSP, Trusted Types).

## Практический рецепт для Angular SPA

1. Если есть возможность держать сервер — **BFF** с `HttpOnly; Secure; SameSite=Strict` cookie.
2. Если API принимает только Bearer-токены и BFF невозможен:
   - Authorization Code + PKCE через проверенную библиотеку;
   - access-токен — **в памяти** (сервис с сигналом);
   - refresh-токен — в `HttpOnly`-cookie, выставленной сервером авторизации, с ротацией; либо refresh через скрытый iframe/повторную авторизацию;
   - короткий срок жизни access-токена.
3. Интерсептор добавляет токен **только для своих API-доменов** (проверка URL), иначе токен утечёт на сторонние запросы.
4. При выходе — отзыв refresh-токена на сервере, очистка памяти, синхронизация вкладок (`BroadcastChannel` или событие `storage`).

```ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const isOwnApi = req.url.startsWith(inject(API_URL));
  const token = inject(AuthStore).accessToken();
  return isOwnApi && token ? next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })) : next(req);
};
```

## Что не делать

- Не храните токены в URL (утекают в логи, историю, `Referer`).
- Не кладите токены в `TransferState` при SSR — они окажутся в HTML.
- Не логируйте токены и заголовки авторизации в системы мониторинга.
- Не держите access-токены живыми по неделе «для удобства».

> [!INTERVIEW]
> «Где хранить токен в SPA?» — Зависит от угроз. `localStorage` прост, но любой XSS читает токен и уносит его. `HttpOnly`-cookie недоступна JS, но требует защиты от CSRF (SameSite и XSRF-токен). Компромисс — access-токен в памяти с коротким сроком жизни и refresh в `HttpOnly`-cookie с ротацией. Самый безопасный вариант — BFF: токены хранятся на сервере, браузер держит только сессионную cookie. При любом варианте XSS позволяет действовать от имени пользователя, поэтому главное — предотвратить XSS.

## Коротко

- localStorage — XSS уносит токен; HttpOnly cookie — защищает от кражи, но нужна защита от CSRF.
- Компромисс: access в памяти + refresh в HttpOnly cookie с ротацией.
- BFF — токены вообще не попадают в браузер.
- Токен — только на свои домены, никогда в URL и TransferState.
- Ни одно хранилище не спасает от XSS — предотвращайте XSS.
