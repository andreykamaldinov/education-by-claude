Change detection (обнаружение изменений) — процесс, в котором Angular сверяет состояние компонентов с DOM и обновляет то, что изменилось. Это самый частый «глубокий» вопрос на собеседовании по Angular: как он работает, когда запускается и как сделать его дешевле.

## Задача

Шаблон связывает DOM с данными компонента:

```html
<h1>{{ title }}</h1>
<app-cart [items]="cartItems" />
```

Когда `title` изменился, кто-то должен обновить текст в `<h1>`. Angular не следит за каждым полем (в отличие от Proxy-реактивности Vue). Вместо этого он в нужные моменты **проходит по дереву компонентов и сравнивает текущие значения биндингов с предыдущими**.

## Две части вопроса

1. **Когда** запускать проверку — задача планировщика: zone.js или zoneless-механизм на сигналах и событиях.
2. **Что** проверять — задача обхода дерева view с учётом стратегий `Eager` / `OnPush` и флагов «грязности».

## Как выполняется проверка

Проверка начинается с `ApplicationRef.tick()`. Для каждого корневого view Angular вызывает обновление, а дальше рекурсивно:

```text
refreshView(view):
  1. выполнить функцию шаблона в режиме обновления:
     для каждого биндинга вычислить выражение и сравнить с сохранённым значением;
     если отличается — обновить DOM / input дочернего компонента
  2. хуки ngDoCheck, ngAfterContentChecked
  3. обработать встроенные view (@if, @for) и проецированный контент
  4. для каждого дочернего компонента — решить, нужно ли его обновлять:
       Eager (бывший Default) → обновить всегда
       OnPush → только если помечен dirty или в нём изменился прочитанный сигнал
  5. хуки ngAfterViewChecked
```

Важные свойства:

- **Однонаправленный поток данных**: проверка идёт сверху вниз, один проход. Родитель передаёт данные ребёнку, но ребёнок не должен менять данные родителя во время проверки.
- **Сравнение по ссылке** (`Object.is`): для объектов и массивов изменение — это новая ссылка.
- Каждый биндинг хранит предыдущее значение в LView — сравнение дешёвое, но выполняется для всех проверяемых компонентов.

## Стратегии компонента

```ts
@Component({
  selector: 'app-price',
  changeDetection: ChangeDetectionStrategy.OnPush, // в Angular 22 — значение по умолчанию
  template: `{{ amount() | currency: 'RUB' }}`,
})
export class Price {
  readonly amount = input.required<number>();
}
```

| Стратегия | Компонент проверяется |
| --- | --- |
| `Eager` (раньше называлась `Default`) | при каждом проходе change detection, если проверяется родитель |
| `OnPush` | только когда: изменилась ссылка input из шаблона родителя; произошло событие из шаблона/host этого компонента или его потомков; вызван `markForCheck()` (так делает `async` pipe); изменился сигнал, прочитанный в его шаблоне |

> [!NOTE]
> С Angular 22 `OnPush` — стратегия по умолчанию: компонент без явного `changeDetection` ведёт себя как `OnPush`. `ChangeDetectionStrategy.Default` переименована в `Eager`, старое имя объявлено устаревшим. Код, который полагался на «проверяй всё всегда» (мутации объектов, поля, меняемые в `setTimeout`), при миграции нужно переписывать на сигналы или явный `markForCheck`. Миграцию помогает выполнить Angular CLI.

## Флаги и «локальная» проверка с сигналами

Каждый view хранит флаги: `Dirty`, `RefreshView`, `HasChildViewsToRefresh` и др.

- `markForCheck()` и события помечают **компонент и всех его предков** как `Dirty` — путь от корня до компонента будет проверен.
- Изменение сигнала, прочитанного в шаблоне, помечает **только этот view** (`RefreshView`), а предкам ставит лишь `HasChildViewsToRefresh`. При обходе OnPush-предки, которые сами не грязные, **не обновляются** — Angular просто спускается через них к нужному view.

```text
App (OnPush)                 ← пройдём, но не будем обновлять
└── Layout (OnPush)          ← пройдём, но не будем обновлять
    └── Sidebar (OnPush)
    └── Cart (OnPush)        ← сигнал cartCount изменился: обновляем только Cart
```

Это и есть главное практическое преимущество сигналов: стоимость обновления пропорциональна тому, что изменилось, а не размеру приложения.

## ExpressionChangedAfterItHasBeenCheckedError

В режиме разработки после каждой проверки Angular выполняет **второй, проверочный проход** (`checkNoChanges`): вычисляет все биндинги ещё раз и убеждается, что значения не изменились. Если изменились — ошибка:

```text
NG0100: ExpressionChangedAfterItHasBeenCheckedError: Expression has changed after it was checked.
Previous value: 'false'. Current value: 'true'.
```

Типичные причины:

```ts
// 1. Ребёнок меняет состояние родителя во время проверки
ngAfterViewInit() {
  this.parent.hasChildren = true; // родитель уже проверен в этом проходе
}

// 2. Геттер, возвращающий новое значение при каждом вызове
get now() { return Date.now(); } // {{ now }} — каждый раз разное

// 3. Изменение данных в ngAfterViewInit / ngAfterViewChecked, которые уже отрисованы
```

Как исправлять — по сути, а не «заворачивать в `setTimeout`»:

- перенести вычисление раньше (в `computed`, конструктор, `ngOnInit`);
- сделать данные сигналом — тогда изменение запланирует новую проверку корректно;
- не менять состояние родителя из ребёнка синхронно во время рендера: используйте output или общий сервис с сигналами.

> [!WARNING]
> В production-сборке проверочного прохода нет, поэтому ошибка не появляется — но UI при этом может показывать устаревшие данные. Ошибка в dev-режиме — это симптом реального бага в потоке данных.

## Ручное управление: ChangeDetectorRef

```ts
export class LegacyWidget {
  private readonly cdr = inject(ChangeDetectorRef);

  onExternalUpdate(data: Data) {
    this.data = data;
    this.cdr.markForCheck(); // пометить компонент и предков; проверка выполнится в ближайшем tick
  }

  renderNow() {
    this.cdr.detectChanges(); // синхронно проверить этот компонент и его детей прямо сейчас
  }
}
```

| Метод | Что делает |
| --- | --- |
| `markForCheck()` | помечает путь до корня как dirty и планирует проверку |
| `detectChanges()` | синхронно проверяет этот view и детей |
| `detach()` / `reattach()` | исключить view из автоматических проверок / вернуть |
| `checkNoChanges()` | dev-проверка, что ничего не изменилось |

`detach()` + ручной `detectChanges()` иногда применяют для виджетов с очень частыми обновлениями (графики, таймеры), чтобы контролировать частоту рендера.

## Что делает проверку дорогой

- Много компонентов со стратегией `Eager` — проверяются всегда.
- Тяжёлые выражения и методы в шаблонах — вычисляются при каждой проверке.
- Нечистые пайпы.
- `@for` без хорошего `track` — пересоздание DOM.
- Частые глобальные события (scroll, mousemove), запускающие проверку всего приложения (актуально для zone.js).

Инструмент диагностики — **Angular DevTools**, вкладка Profiler: показывает, сколько длился каждый цикл проверки и какие компоненты в нём участвовали. В консоли можно вызвать `ng.profiler.timeChangeDetection()` (при включённом `enableDebugTools`).

> [!INTERVIEW]
> «Как работает change detection в Angular?» — Когда планировщик (zone.js или, в zoneless-режиме, сигналы, события шаблона и `markForCheck`) решает, что состояние могло измениться, вызывается `ApplicationRef.tick()`. Angular обходит дерево view сверху вниз, для каждого проверяемого компонента вычисляет выражения биндингов и сравнивает их с предыдущими значениями, обновляя DOM при отличиях. Компоненты `OnPush` (по умолчанию в Angular 22) проверяются только если помечены: новый input, событие, `markForCheck`, изменение сигнала из шаблона. Сигналы позволяют обновлять конкретный view, не обновляя его предков. В dev-режиме второй проход проверяет, что значения стабильны, — отсюда `ExpressionChangedAfterItHasBeenCheckedError`.

## Коротко

- Change detection = обход дерева view и сравнение значений биндингов с предыдущими.
- «Когда» решает планировщик (zone.js или zoneless), «что» — стратегия и флаги компонента.
- `OnPush` по умолчанию в Angular 22; `Default` переименован в `Eager`.
- Сигналы помечают конкретный view — предки-OnPush не обновляются.
- `ExpressionChanged...` — симптом нарушения однонаправленного потока данных.
