Микрофронтенды переносят идею микросервисов на клиент: интерфейс делится на части, которые разрабатывают, тестируют и **развёртывают независимо** разные команды. Это решение организационных проблем — и источник новой технической сложности.

## Зачем

- Несколько команд (5+) работают над одним большим продуктом и мешают друг другу: общий релиз, общий репозиторий, конфликты.
- Нужны независимые релизы частей продукта (каталог выкатывается 10 раз в день, личный кабинет — раз в неделю).
- Постепенная миграция легаси (AngularJS → Angular, Angular → другой фреймворк) по кусочкам ([Strangler Fig](/tracks/architecture/microservice-patterns)).
- Вертикальные команды, владеющие доменом от БД до UI (bounded contexts из [DDD](/tracks/architecture/ddd)).

## Когда не нужно

- Одна-две команды: монорепозиторий с модулями (Nx) даст изоляцию без накладных расходов.
- Нет ясных границ доменов.
- Нет инфраструктуры для независимого деплоя и мониторинга.

Микрофронтенды — это **цена**: дублирование зависимостей, сложность общей навигации и состояния, консистентность дизайна, интеграционное тестирование.

## Способы композиции

| Подход | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| **Серверная** (SSI, edge, фрагменты) | сервер собирает HTML из фрагментов команд | быстрая загрузка, SEO | сложная интерактивность между частями |
| **Сборочная** (npm-пакеты) | части — библиотеки, собираются в одно приложение | просто, один бандл | **нет независимого деплоя** — каждое изменение требует пересборки хоста |
| **iframe** | каждая часть в своём iframe | полная изоляция | плохой UX: размеры, навигация, доступность, производительность |
| **Web Components** | части — custom elements | технологически нейтрально | общие зависимости, стили, SSR — вручную |
| **Runtime-композиция модулей** (Module/Native Federation) | хост загружает удалённые модули во время выполнения | независимый деплой, общие зависимости, нативная интеграция | версии shared-библиотек, сложность конфигурации |
| **Маршрутизация** (single-spa и аналоги) | оркестратор монтирует приложения по URL | разные фреймворки на одной странице | общий layout и состояние — вручную |

Для Angular-экосистемы стандарт — **runtime-композиция**: Module Federation (Webpack) и Native Federation (esbuild/import maps). Подробно — в треке сборки: [Module Federation](/tracks/tooling/module-federation), [Native Federation](/tracks/tooling/native-federation).

## Анатомия

```text
Shell (host): layout, навигация, аутентификация, загрузка remote-ов
  ├── /catalog  → remote «Каталог» (команда A, деплоится отдельно)
  ├── /cart     → remote «Корзина» (команда B)
  └── /account  → remote «Кабинет» (команда C)
Общие: Angular, RxJS, дизайн-система (shared, singleton)
```

### Нарезка

- **Вертикально по доменам/маршрутам** (рекомендуется): каждый remote — набор страниц домена. Минимум взаимодействия между частями.
- **Горизонтально по виджетам**: несколько remote-ов на одной странице (шапка от одной команды, рекомендации — от другой). Больше взаимодействия, сложнее.

## Коммуникация между микрофронтендами

Чем меньше — тем лучше. Варианты от слабой связи к сильной:

1. **URL** — параметры маршрута и query (самое простое и надёжное).
2. **Браузерные события** — `CustomEvent` на `window` или `BroadcastChannel`:

```ts
// Корзина сообщает
window.dispatchEvent(new CustomEvent('cart:changed', { detail: { count: 3 } }));
// Шапка shell-а слушает
fromEvent<CustomEvent<{ count: number }>>(window, 'cart:changed');
```

3. **Общий сервис из shared-библиотеки** (singleton через федерацию) — удобно, но связывает версии.
4. **Общий глобальный стор** — антипаттерн: возвращает связанность монолита.

Контракты событий — такой же публичный API, как REST: типизируйте и версионируйте их в общей библиотеке.

## Общие вопросы

- **Дизайн-система**: общая библиотека компонентов и токенов, иначе продукт превращается в лоскутное одеяло.
- **Аутентификация**: shell отвечает за вход; remote-ы получают пользователя через общий сервис или токен.
- **Версии зависимостей**: Angular и RxJS должны быть общими singleton-ами одной мажорной версии, иначе два экземпляра Angular на странице.
- **Стили**: изоляция (инкапсуляция Angular, префиксы, Shadow DOM) — чтобы CSS одной команды не ломал другую.
- **Производительность**: следите за дублированием библиотек и количеством запросов.
- **Тестирование**: контрактные тесты событий и интерфейсов, E2E на собранной системе.
- **Устойчивость**: недоступный remote не должен ронять shell — fallback-страница и обработка ошибок загрузки.

> [!INTERVIEW]
> «Когда оправданы микрофронтенды и какие есть подходы?» — Когда несколько независимых команд работают над большим продуктом и им нужны независимые релизы, или при постепенной миграции легаси. Подходы: серверная композиция фрагментов, iframe, Web Components, сборочная интеграция через пакеты (без независимого деплоя) и runtime-композиция через Module/Native Federation — стандарт для Angular. Нарезать лучше вертикально по доменам, общаться минимально (URL, события), общие Angular/RxJS делать singleton-ами, а дизайн-систему — общей библиотекой.

## Коротко

- Микрофронтенды решают организационные задачи: независимые команды и релизы.
- Для 1–2 команд достаточно модульного монорепозитория.
- Для Angular — runtime-композиция через Module/Native Federation.
- Нарезка по доменам; коммуникация через URL и события, без общего стора.
- Общие дизайн-система и singleton-зависимости, устойчивость к отказу remote.
