В микросервисной системе ключевые вопросы — как сервисы общаются между собой и как клиент (фронтенд, мобильное приложение) получает данные, разбросанные по десятку сервисов. Разберём протоколы, синхронное и асинхронное взаимодействие, API Gateway и BFF.

## Синхронное взаимодействие

Сервис отправляет запрос и ждёт ответ.

| Протокол | Формат | Особенности | Где |
| --- | --- | --- | --- |
| REST / HTTP+JSON | текст | простой, кешируемый, понятный | публичные API, фронтенд ↔ бэкенд |
| gRPC | Protobuf поверх HTTP/2 | строгие контракты, кодогенерация, стриминг, быстрый | сервис ↔ сервис |
| GraphQL | запрос описывает форму ответа | клиент выбирает поля, одна точка входа | фронтенд ↔ агрегатор |

Проблема синхронных цепочек: если A ждёт B, B ждёт C, а C тормозит — тормозит всё. Доступность цепочки = произведение доступностей (три сервиса по 99,9% дают ≈ 99,7%).

## Асинхронное взаимодействие

Сервис публикует сообщение в брокер и не ждёт ответа. Подписчики обрабатывают его, когда могут.

```text
Заказы ──OrderPlaced──▶ [брокер] ──▶ Склад (резервирует товары)
                               ├──▶ Уведомления (отправляют письмо)
                               └──▶ Аналитика (обновляет отчёты)
```

- **Слабая связанность**: заказы не знают, кто подписан на событие.
- **Устойчивость**: если уведомления недоступны, сообщение подождёт в очереди.
- **Сложность**: eventual consistency, порядок сообщений, повторная доставка, идемпотентность.

Подробнее — [Событийная архитектура](/tracks/architecture/event-driven).

## API Gateway

Единая точка входа для внешних клиентов:

```text
Браузер / мобильное ──▶ API Gateway ──▶ Каталог
                          │  auth      ├──▶ Заказы
                          │  rate limit├──▶ Пользователи
                          │  routing   └──▶ Оплата
                          │  TLS, CORS
```

Функции шлюза:

- маршрутизация запросов к сервисам (`/api/orders/*` → сервис заказов);
- аутентификация и проверка токенов в одном месте;
- rate limiting, квоты, защита от злоупотреблений;
- TLS, CORS, сжатие, кеширование;
- иногда агрегация ответов нескольких сервисов.

Примеры: Kong, NGINX, Envoy, облачные API Gateway (AWS, GCP, Yandex Cloud).

## BFF — Backend for Frontend

Отдельный бэкенд-слой **под конкретный клиент**: веб, мобильное приложение, партнёрский API.

```text
Веб (Angular) ──▶ Web BFF ────┐
Мобильное    ──▶ Mobile BFF ──┼──▶ микросервисы
Партнёры     ──▶ Public API ──┘
```

Зачем:

- **Агрегация под экран**: один запрос `GET /bff/order-page/42` вместо пяти запросов к сервисам и склейки в браузере.
- **Форма данных под клиент**: мобильному — меньше полей, вебу — больше.
- **Безопасность**: BFF хранит OAuth-токены, браузер получает только `HttpOnly`-cookie ([Где хранить токены](/tracks/security/token-storage)).
- **Владение**: BFF часто пишет и поддерживает **команда фронтенда** (на Node.js/NestJS), что ускоряет изменения под UI.

Риск — превращение BFF в «монолит-посредник» с бизнес-логикой. Правило: BFF агрегирует и адаптирует, а бизнес-правила остаются в сервисах.

```ts
// Упрощённый Web BFF на NestJS: агрегация для страницы заказа
@Get('order-page/:id')
async orderPage(@Param('id') id: string) {
  const order = await this.orders.get(id);
  const [customer, delivery] = await Promise.all([
    this.users.get(order.customerId),
    this.delivery.status(order.id).catch(() => null), // частичный отказ не ломает страницу
  ]);
  return { order, customer: { name: customer.name }, delivery };
}
```

## GraphQL federation

Альтернатива BFF: каждый сервис публикует свою часть графа, шлюз (Apollo Router и аналоги) объединяет их в единую схему. Клиент одним запросом получает данные из нескольких сервисов в нужной форме.

## Service Discovery

Сервисы запускаются и останавливаются динамически (контейнеры, автомасштабирование). Как найти адрес сервиса заказов?

- **Клиентский discovery**: сервис спрашивает реестр (Consul, Eureka) и сам выбирает экземпляр.
- **Серверный discovery**: запросы идут через балансировщик, который знает актуальные экземпляры.
- **Kubernetes**: DNS-имя сервиса (`orders.default.svc.cluster.local`) — платформа делает discovery и балансировку сама.

## Наблюдаемость

Без неё микросервисы не отлаживаются:

- **Распределённая трассировка** (OpenTelemetry): один `trace-id` проходит через все сервисы. Фронтенд может инициировать трассировку, передавая заголовок `traceparent`.
- **Централизованные логи** с корреляцией по trace-id.
- **Метрики и алерты**: задержки, ошибки, насыщение.

> [!INTERVIEW]
> «Чем API Gateway отличается от BFF?» — API Gateway — общая точка входа для всех клиентов: маршрутизация, аутентификация, rate limiting, TLS. BFF — бэкенд, созданный под конкретный клиент (веб, мобильное), который агрегирует данные нескольких сервисов в форму, удобную экрану, и может хранить токены вместо браузера. Часто их используют вместе: клиент → BFF → (gateway) → сервисы.

## Коротко

- Синхронно: REST, gRPC, GraphQL — просто, но цепочки хрупкие.
- Асинхронно: брокеры сообщений — слабая связанность, eventual consistency.
- API Gateway — единая точка входа и сквозные задачи.
- BFF — агрегация и адаптация под конкретный клиент, часто во владении фронтенд-команды.
- Discovery и наблюдаемость (трассировка) — обязательная инфраструктура.
